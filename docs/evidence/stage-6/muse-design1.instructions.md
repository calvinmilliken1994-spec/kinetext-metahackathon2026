## Product direction (binding, from the product owner)
- The product must SUMMARISE ANY PAGE QUICKLY AND ACCURATELY and turn it into DEMONSTRATIONAL VISUALS and INTERACTIVE COMPONENTS for teachers (secondary school / intro university; predict-then-reveal in a lecture). It is NOT a fact checker. Checks are a quiet trust layer underneath: they verify what is cheap and exact (quotes are verbatim from the page, numbers/formulas are computed by our code, structure is valid). Never claim that content is "true"; the claim is "this is what the cited sentence says".
- Today (5b evaluation of 29 real pages) only 9 became a lesson, 17 were DECLINED and 3 FAILED (2 output truncated, 1 invalid analysis) because only 8 hand-built activity types exist (7 numeric closed-form engines and a dated-events timeline). Goal: no dead-end declines; a decline is reserved for unusable sources.
- Layer 1: a shared component kit that works on any page. Layer 2: subject engines = shared kit + subject-specific components + subject guidance for Muse + subject checks. Simulations (the existing numeric engines) and timelines remain the premium outputs; keep them, and have the component plan prefer a premium engine only when its `appliesWhen` genuinely fits.

## Hard rules (a design that breaks any of these is rejected)
1. Muse authors DATA, never executable code. No generated code is executed (no eval, no Function, no dynamic import, no WebAssembly from Muse). Formulas are strings in a tiny safe expression language parsed by OUR parser into an AST and evaluated by OUR tested evaluator.
2. Muse must not invent content. Every claim shown to the student must be tied to a verbatim quote from the page (<=150 characters, copied character-for-character from one paragraph, no ellipsis, whitespace-normalised comparison, each with the exact sourceId). Anything not quoted (titles, instructions, distractors, hints) is labelled by the UI as written by AI and must not assert new facts. Numbers appearing in AI-written text must be checkable against the page (design a cheap deterministic rule).
3. Structured output constraint: the generation schema has every key REQUIRED (no optional keys); use sentinels like 0 or "" (the timeline engine uses month = 0 for "not stated"). Strings are plain text (no markdown/HTML). Keep gen schemas small: output truncation killed 2 of 29 pages already, so each Muse call must have a small, bounded output (state a target output-token budget per call).
4. Untrusted input: the page text and any model output travel in untrusted-data blocks with boundary tags; repair findings are untrusted data; repair is authorised ONLY by validator-owned `affected` JSON-pointer paths recomputed from revision 1 (never from message text); a repair may never weaken (fewer items, looser tolerances) and keeps ids stable. The existing repair loop does this for numeric/timeline specs and for the analysis; extend the same discipline per component.
5. Never attribute statements to the publisher ("according to NASA"), never name the publisher in generated text; sources carry their attribution/licence separately. Student-facing generated text is labelled AI-generated.
6. Decline integrity: a decline is honest and reserved for UNUSABLE sources only: you must define exact criteria (for example text too short or not prose, boilerplate/navigation/legal text only, no teachable content, unreadable or non-language text, instructions-to-the-AI only). The existing 17 declines were mostly a missing-engine problem and must now produce an overview plus components.
7. Teaching-margin grading rule for numeric predictions: margin = max(case tolerance, 2% of the engine value); the UI shows the engine value.
8. The existing checks stay light: "quotes verbatim; formulas computed by our code; no AI-written code executed". Do not add heavyweight NLP/LLM-in-the-loop verification. Do not propose an AI judge for truth. Cheap structural/lexical checks are fine (for example "the item's label appears in its quote", "quote offsets ascend in source order").

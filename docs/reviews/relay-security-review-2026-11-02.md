# Stage 11 relay security review — 2026-11-02

Scope: independent review of the checked-out Stage 11 relay and local relay mode; no live endpoint calls or secret files. Commit identity was not independently checked because Git was prohibited.

## Ranked summary

1. **High:** durable budget reservations are missing and state-write errors are swallowed; crashes or restarts can reopen spent headroom.
2. **High:** the shared access code travels in Spark Open URL paths and may be captured by infrastructure logs.
3. **High:** reservation estimates are not enforced upper bounds; unvalidated request options and reconciliation after the call permit cap overruns.
4. **Medium:** pause can be bypassed by a request held open while its body is read; already-dispatched calls may continue.
5. **Medium:** upstream responses, including errors, are returned unsanitized; credential exposure depends on upstream reflection.
6. **Medium:** real Modal client identity and shared-IP behavior of the in-memory failed-auth limiter are unverified.
7. **Low:** long-request 303 result URL security and logging need deployment-specific verification.

## Findings

### High — reservations and charges are not durable across crashes or write failure
`relay/relay_core.py:314-317, 382-388, 470-505`; `relay/app.py:34-37`. Reservations exist only in process memory and are persisted only after a request completes. A container crash/restart while requests are in flight loses the reservations and may lose already-incurred upstream charges; the replacement can spend the same headroom again. Further, `_persist` swallows store write failures and keeps admitting requests; a later restart reloads the stale total. `max_containers=1` does not preserve in-flight state across restarts. Fix: durably and atomically reserve before forwarding, reconcile afterward, retain conservative charges for orphaned reservations, and fail closed on any ledger read/write uncertainty; use a transactional store and fencing if concurrent instances can overlap.

### High — access code is included in the Spark Open URL
`apps/api/relay-clients.ts:60-67`; `relay/relay_core.py:252-255, 281-284`. The bearer-equivalent shared code is part of every Spark Open request path. Although the relay's own application log uses a fixed route label, reverse proxies, Modal edge/access logs, HTTP instrumentation, tracing and error reporting may record full URLs. This is a real exposure surface, not proof Modal currently logs these paths. Anyone with the URL can use the shared budget. Fix: move the code to a non-Modal-stripped Authorization or dedicated custom header and verify it survives the deployed edge; redact access logs/traces, rotate the existing code after migration, and review URL retention and access. Avoid treating URL encoding as protection.

### High — request reservation is not an upper bound; actual charges can exceed cap
`relay/relay_core.py:186-193, 465-474, 484-505`. Admission assumes one completion and input tokens <= raw bytes / 3, while forwarding arbitrary additional model parameters unchanged. A caller can send `n`, `stream`, both competing max-token fields, multimodal URLs, or other provider-supported cost-bearing options; whether each is accepted and its billing semantics are provider-dependent. Even an ordinary input can tokenize more densely than one token per three bytes; actual usage is only reconciled *after* spend, with no limit on overruns. Streaming without usage falls back to the same potentially underestimated reservation. SAM likewise reserves a fixed per-call amount without restricting inputs to one billable image (`relay/relay_core.py:470, 511-512`); acceptance/billing of multi-image or video requests is unverified. Local mocked probe: a request admitted with cap $0.001 and `max_tokens=1` incurred simulated usage of $0.0055, which the relay persisted; `n=50` and `stream=true` passed through. This proves absence of enforcement, not that the real provider accepts those options or billed the mock. Fix: strict per-route schemas, reject streaming and unsupported cost-bearing fields, enforce bounded output and number of choices, allow only one validated SAM image where per-image billing applies, and use provider-verified conservative upper bounds (including multimodal input). Reconcile discrepancies and stop on unknown billing; provider-side spend limits are the ultimate hard backstop.

### Medium — pause is checked before reading the body, not at dispatch
`relay/relay_core.py:461-487`. A request admitted while enabled can slowly send its body, remain in `request.stream()`, and be forwarded even after the operator pauses. The upstream may also continue work already dispatched at pause time. An offline ASGI mock reproduced pause after the first state check and before body completion: the upstream received the request and the client got 200. Fix: recheck the shared switch immediately before reservation/dispatch, bound body-read time and concurrency, and explicitly document/cancel in-flight work if the desired kill-switch semantics require it. Even rechecking has a small cross-system race; a strict stop requires coordinated admission/dispatch fencing.

### Medium — real upstream response body, including errors, is relayed unsanitized
`relay/relay_core.py:484-493`; `relay/tests/test_relay.py:638-645`. The module header says upstream error text is never echoed, but the implementation returns all upstream bodies byte-for-byte, including non-200 errors. If a provider reflects its Authorization/Modal credentials, URLs, or internal details in an error, any code holder can retrieve them; no actual provider reflection has been demonstrated. An offline mock confirmed a synthetic upstream key in a response is returned verbatim. Fix: map upstream failures to fixed errors; carefully filter successful JSON or at least redact known credentials in all textual outputs, and add secret-reflection tests. This is distinct from transport exceptions, which are sanitized.

### Medium — failed-auth limiter depends on unverified proxy client identity
`relay/relay_core.py:330-355`; `relay/app.py:36-43`. The limiter keys solely on ASGI `request.client.host`; code and local tests do not establish whether Modal supplies the end-user IP or its edge IP. If shared edge IPs are presented, ten unauthenticated failures can block valid users on that edge for a minute; if an untrusted forwarded header is implicitly used by the ASGI stack, it might instead be spoofable. The limiter is also process-local and resets on restart; a distributed attacker can rotate addresses. Fix: verify Modal's documented and deployed proxy/ASGI identity behavior, use only a trusted edge-provided normalized client identity, implement shared/distributed limits and protect legitimate users from shared-IP lockouts. Do not blindly trust client-supplied X-Forwarded-For.

### Low — 303 result URLs and redirects need deployment-specific access review
`relay/app.py:34-38`; `packages/meta/client.ts:683`; `docs/evidence/stage-11/live-checks.md:18`. The client follows Modal's long-running 303 automatically; observed operation does not establish whether the result URL is bearer-accessible, how long it lives, or what logs retain it. If anyone possessing the URL can retrieve the response, it is another sensitive capability; redirect destinations also require trust. Fix: verify Modal's current result URL authorization, lifetime, redaction, and redirect origin guarantees without publishing a real result URL; constrain destinations where compatible with Modal, and document residual risk.

## Checked and fine / limitations

- Ran `PYTHONDONTWRITEBYTECODE=1 python -m pytest relay -q -p no:cacheprovider`: **98 passed, 1 skipped** (Modal wiring suite skipped; local installed dependencies, no installs). Existing passing tests do not prove the hard cap or production edge behavior.
- Offline ASGI/MockTransport probe used only synthetic credentials and did not contact a network; confirms late-pause dispatch, response passthrough, arbitrary `n`/`stream` forwarding, and an over-cap simulated reconciliation. Probe: profile scratch `review-relay/probe.py`.
- `apps/api/main.ts:265-267` binds explicitly to `127.0.0.1`; it is not LAN-bound by default. Host checks apply to every request and Origin checks cover access and job writes (`server.ts:318-347, 729-747, 853-875`). Missing Origin is accepted for non-browser clients; cookies are HttpOnly/SameSite=Strict. No CORS allow-all header was identified in the reviewed server. These are not defenses against malicious same-machine processes.
- JSON duplicate keys (including nested keys) and non-finite values are rejected; exact case-sensitive model comparison and fixed route-to-upstream mapping with redirects disabled prevent the obvious allowlist/open-proxy bypasses (`relay_core.py:218-239, 275-285, 390-396, 465-481`). Real upstream semantics and the trusted deployment configuration were not independently verified.
- Static handler rejects decoded backslashes, dot-prefixed segments and colons, then compares resolved real paths and serves regular files only (`static.ts:69-115`); no exploitable Windows traversal was established by inspection. Symlink/junction mutation between check and open is a possible local filesystem race, not tested; Windows 8.3 aliases and filesystem behavior were not exhaustively probed.
- `start.mjs` uses fixed command strings and argument-array browser launch, not interpolated shell commands; env values are not directly printed by its loading code. No `.env` or secret files were read. Installed tools, third-party build scripts, deployed Modal logging and browser runtime were not audited, so no blanket no-leak claim is made.
- Read-only review except this requested report and the authorized scratch probe. No deployed relay or live endpoint was called, no git or package installs were used, and no production files were changed.

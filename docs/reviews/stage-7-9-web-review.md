# Stage 7–9 web code review

**Reviewer:** GPT-6.1 Sol, independent OpenAI review, High reasoning.

**Verdict: changes required.** The build and current tests pass. The review found correctness gaps at the view/validator boundary, two reproducible presentation reveal failures, and replay/onboarding edge cases. This is not public-deployment approval.

## Scope and method

- Reviewed `git diff c2c849a^ f2a64f08b883776afec1d661ff8ed3eb5aa26d34 -- apps/web`. Read the Stage 7, 8a, 8b, 9 and 9b specs. Read the shared engines and relevant validators to check view assumptions.
- Ran web library tests, the production build and root typecheck. Used a separate `rev-web` browser session against localhost. `/api/health` reported `live:false`, `busy:false`.

- Throwaway scripts and JSON results are in the profile's local scratch `review/` directory, not committed. Synthetic mutations below are review probes, not model outputs or changes to recorded evidence.

Severity: **High** = wrong checked teaching output or potentially unbounded browser work. **Medium** = broken teaching/replay behavior on a supported path. **Low** = robustness or accessibility edge case.

## Test gaps and regression targets

The current tests mostly exercise pure view models. They do not establish the composed React behavior reproduced here.

1. Validate a spec, then render exactly that accepted spec. Cover W-01, W-02, W-03, W-06 and W-09. Pin the boundary between accepted data and visible meaning.
2. For each presentation ask beat, test pre-R text, accessible names, hover/focus quote zone, and R→interaction→←. W-04 and W-05 are absent from the pure reducer/reveal tests.
3. Traverse the whole fallback tour rather than checking only the filtered step ids. Include missing recording, fetch failure and focus restoration.
4. Exercise replay through App's activity/outcome branches. The replay unit tests only establish snapshot transformations, not persistent labelling.
5. Reject invalid calculator input as input, not as a component render exception.

## Deployment notes

These are prerequisites for the planned Render release, not changes made by this review.

- **Same-origin root hosting fits the client.** `api.ts:125–150`, figure loading and replay fetches use `/api/...`; there is no production API-base setting. Serve the static app and API at the same origin, with `/api` routed before the SPA fallback. Hosting under a path prefix or on a separate API origin needs an explicit shared base, including replay and figure URLs. The Vite proxy is development-only.
- **The current executable is still loopback-oriented.** `apps/api/main.ts:194` binds `127.0.0.1`; `server.ts:112,272–276` defaults to loopback/development hosts. The current source does not provide the requested Render public bind, static bundle integration and public HTTPS origin policy. Do not deploy the dev server as the solution. Client error copy in `api.ts:154,161–162` also sends users to local ports and needs production wording.
- **`live:false` is not a public read-only authorization mode.** It disables job generation, but `NewLessonSection` still offers Paste your own text (`PipelinePanel.tsx:73–84`). `handleCreateSource` checks Origin and format, then writes a source without a live/access gate (`apps/api/server.ts:544–598`). This was established by reading code; no POST was attempted. Gate all write routes server-side. Disabling a Generate button is insufficient.
- **Judge authorization is not wired into this client.** `api.createJob` sends only the content-type header and request body. Add the server-validated access-code/session contract, per-judge admission controls and kill switch before exposing generation. Do not put provider keys or a reusable judge secret into Vite variables, localStorage or the bundle.
- **Ship the recording used by onboarding.** It depends on the fixed `TOUR_JOB_ID`, its lesson artifacts, source and figure bytes. Test the actual deployment package with an empty runtime disk, not the developer's existing storage. W-08 matters when that package is incomplete.
- Bundle size is a performance warning, not a failing build. Presentation and infrequently used engine views are candidates for lazy loading after correctness fixes.
